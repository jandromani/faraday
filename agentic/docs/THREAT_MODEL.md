# FARADAY Preview Threat Model

Status: internal working model, 2026-10-29. No independent review or production approval. Priorities are qualitative judgments, not measured probabilities: P0 means a plausible path to unauthorized effects, credential exposure or unsafe recovery; P1 means a significant availability, privacy or evidence risk. Controls marked required are deployment requirements, not claims that FARADAY implements them. Owners are accountable roles to be assigned by the operator, not named or staffed teams.

## Scope and trust boundaries

Assets: issuer and agent private keys, backend credentials, signed capabilities and approvals, RPC arguments and results, graph metadata, policy/configuration, journals, receipts and audit records. Attackers can control untrusted tool output, prompts, MCP requests and network peers; a malicious local process, compromised operator, host administrator, trusted backend or signing key can exceed the guarantees of the preview.

| Topology | Boundary and existing controls | Required before use beyond fixtures | Evidence limit |
| --- | --- | --- | --- |
| T1: local discovery, proxy and viewer | Config and MCP traffic cross into the operator's process; only traffic routed through the proxy receives its optional tool allowlist. Viewer listens on loopback with a token. | Operator: trust configured executables; restrict filesystem and network access; protect backups and local sessions. Security owner: verify ACLs on the target OS. | Discovery is not execution mediation; direct tool/API access and malicious child processes remain possible. Windows automatic installation is disabled until backup ACL protection is verified. |
| T2: synthetic loopback pilot | Client-supplied request, proof and optional OAuth cross into gateway; Authority verifies capability, proof and policy; gateway calls a fixed backend and records signed evidence. | Identity owner: manage and rotate keys. Policy owner: configure deny-by-default rules. Deployment owner: ensure mandatory mediation, secure credentials and TLS where remote. | Tests use synthetic tools and keys; no general workload attestation, KMS, production sandbox or effect verification. |
| T3: synthetic Compose pilot | Agent, gateway and backend occupy separate container network zones; only gateway joins both. Fixture enables unencrypted backend HTTP. | Deployment owner: enforce network segmentation, encrypt and authenticate service traffic, protect mounts/secrets, validate limits and direct-bypass attempts in the actual deployment. | Historical isolation evidence covers an earlier fixture, not every deployment. Current Compose changes require a fresh Docker execution. A privileged host can bypass container boundaries. |

## Attack trees

### A1: cause an unauthorized backend effect (TM-01, TM-02, TM-03, TM-11, TM-12)

Root: backend performs an action outside approved scope. Branches: (1) bypass gateway with direct backend access and obtain its secret; (2) forge or steal accepted identity and capability, then satisfy proof and policy; (3) induce a legitimately authorized tool to use excessive authority; (4) change policy while a request waits. Required barriers: network and secret separation, authenticated workload and exact scope, protected policy recheck, and real resource-level controls. A passing fixture demonstrates only its exercised branches.

### A2: conceal or duplicate an effect (TM-04, TM-05, TM-06, TM-10)

Root: operation occurs without trustworthy, reconcilable evidence. Branches: forge an attestation; alter local journal or signing key; return an ambiguous response and induce a blind retry; lose durable state during failure. Required barriers: separate protected signers, durable externally protected records, backend idempotency and read-only reconciliation. Current local signatures and SQLite do not provide independent real-world proof or distributed recovery.

### A3: extract a credential or sensitive context (TM-07, TM-08, TM-13)

Root: attacker obtains a credential, argument or sensitive metadata. Branches: read a backup or mount; intercept unencrypted fixture traffic; redirect a request or target a private service; use an authorized external metadata transfer. Required barriers: verified OS permissions, scoped short-lived secrets, authenticated encryption, network egress controls and explicit data-sharing approval. The optional free-model check is not a privacy or billing guarantee.

## Review and change control

The security owner must assign named accountable people before deployment, review this model when trust boundaries or supported topologies change, record acceptance of residual risks, and request an independent review. Changes to a critical control require its referenced negative tests plus topology-specific verification. Missing or skipped verification blocks a production claim; no current test establishes universal no-bypass, full STRIDE coverage or regulatory compliance.
